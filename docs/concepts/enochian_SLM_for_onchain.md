# Lighthouse Engine and Governor Dialog Framework (LLM-Free Design)

## Part 1: Lighthouse Engine Design (On-Chain Knowledge Base)

### Data Organization & On-Chain Storage

To meet Bitcoin Ordinals constraints (\~4 MB per inscription), the knowledge libraries and game data are split into **modular, compressed JSON chunks**. The project’s data is already organized by type – e.g. **governor profiles, knowledge base, questlines** – which naturally guides the on-chain storage structure. We use a **zip-inscribed library per module** (or per topic) so each piece remains under the size limit. For example: one inscription might contain the entire “Lighthouse” knowledge base or be further split by tradition if needed, and each governor’s dialog/quest script can be stored in that governor’s own inscription. All data stays in plain JSON (ASCII only) as required, then compressed to maximize use of the 4 MB limit. The first part of each library contains an **index or manifest** for quick lookup of contents, with the bulk data following in linked chunks. This “**index-first**” layout means that when the library is loaded, the client can read the index to find which file or offset contains a given entry, rather than scanning everything.

Each **knowledge entry** in the Lighthouse is a structured JSON object with fields like `id`, `tradition`, `title`, `summary`, `full_content`, `tags`, etc.. These entries are curated and **blockchain-optimized** (500–1000 word content) to preserve sacred wisdom on-chain. The Lighthouse will permanently store all 17 wisdom traditions as immutable on-chain knowledge blocks. By assigning each tradition or category its own section (or separate file), we ensure localized updates and easy retrieval of just the needed segment (e.g. load only “Kabbalah” entries when relevant). A top-level **manifest inscription** (or a well-known index file) can list all other inscription IDs and their contents (like a table of contents of libraries), enabling the Trac indexer to discover and validate all parts of the knowledge base.

### Compression, File Layout, and Unpacking Strategy

We use standard compression (e.g. ZIP/Deflate) on each JSON library to reduce size. Each library file will embed a small header (the index) that maps logical identifiers to byte ranges or to sub-files within the archive. For instance, the **dialog library for a governor** could be a zip file where file names correspond to dialog categories (greetings, hints, lore answers, etc.) and each contains an array of lines. The **Lighthouse knowledge library** might be one JSON file per tradition inside a zip, plus an index file listing all entry IDs and their location. This way, the game client can open the compressed inscription, read the index first, then seek directly to the relevant entry’s compressed data. All decompression happens client-side (since on-chain execution is not possible) – the on-chain role is to **store** data, while the player’s device (or a P2P node running the game) handles **retrieval and decompression**. We ensure the compression algorithm chosen is one that can be implemented in-browser or in-app with minimal overhead (for example, standard ZIP libraries or even a custom lightweight decompressor for deterministic platforms).

**On-chain verification:** using the TAP protocol and Trac indexer, each library’s integrity can be verified. The manifest will include expected hashes or TAP tokens that correspond to each content piece, so nodes can validate that the data hasn’t been altered. The deployment uses an atomic inscription manifest – all chunks are published and referenced together, enabling a **zero-infrastructure** distribution (no servers; data is fetched from Bitcoin directly). In practice, when a player needs a piece of lore or dialog, the game queries the Trac indexer for the inscription containing that content (using the index). The indexer (which tracks all game inscriptions by ID) returns the content, the client decompresses it, and uses it in-game. This strategy achieves a **fully on-chain knowledge base** – the “Lighthouse” – with efficient lookup and minimal duplication.

### On-Device Search & Indexing (LLM-Free)

Without any LLM to semantic-search the knowledge, we implement a **deterministic, local search index** on the client side. Each knowledge entry comes tagged with keywords and cross-references (see the `tags` and `related_concepts` fields in the schema), which we leverage for lookup. We generate a lightweight **inverted index** mapping important keywords to entry IDs (and store this in the library’s index section). A user query can be tokenized and matched against this dictionary to retrieve relevant entries. For example, if the player asks about “True Will”, the engine finds that keyword in the index and directly pulls the Thelema entry on True Will. This keyword index is stored as JSON (or a minimal key-value structure) at the start of the knowledge library for quick access.

For more flexible matching (to handle synonyms or conceptually similar queries), we incorporate a **simple embedding-based similarity lookup** – entirely on-device and pre-computed. The idea is to use a small set of precomputed word or phrase embeddings for the knowledge base, enabling semantic matching without an AI model. In fact, the repository implements a *“lightweight word embedding similarity”* engine that uses pre-defined 50-dimensional vectors and cosine similarity to match text, designed for on-chain feasibility. We adopt a similar approach for the Lighthouse: for each knowledge entry, we store either a vector representation (e.g. embedding of its title/summary) or a representative set of keywords. When the player’s question is parsed, the engine either averages known word vectors or looks up similar terms via a small embedding dictionary, then finds the closest entries by cosine similarity. The embedding math (dot products, etc.) is simple enough to do in the app and is deterministic for all players. The key is to keep the vector data small – e.g. 50-100 dimensions for a limited vocabulary – and **identical across all nodes** so that everyone gets the same results given the same input (important for consensus in a P2P game).

If vector search proves too heavy, the fallback is a robust **tag and keyword search**. The knowledge entries are written with concise titles and tagged with relevant terms (e.g. a Kabbalah entry might have tags like “sephirot, Tree of Life”). The engine can do a simple substring or tag match to surface those entries. Additionally, cross-reference links (`related_concepts`) can help – if one entry is found, the engine can also suggest related entries. This ensures that even without semantic embeddings, the user can navigate the knowledge base via hyperlinked concepts.

**Summary:** The Lighthouse engine uses structured JSON data and a combination of indices, tags, and lightweight embedding math to allow fast, LLM-free lookup of “esoteric knowledge” on-chain. It preserves canonical wisdom in a permanent store and makes it queryable with deterministic algorithms.

## Part 2: Governor Dialog & Quest Engine (LLM-Free NPC Interactions)

### Dialog System Architecture (State Machines & On-Chain Libraries)

Each Governor (NPC) uses a **deterministic state machine** to manage dialogue and quests, rather than generating text with an AI model. Every possible dialogue node and response is pre-written and stored in the on-chain dialog library for that governor. We model each encounter as a directed graph of dialogue nodes, where edges are conditional transitions based on the player’s input or game state. For example, a governor’s dialog might start at an **Introduction** node, then branch into a **Riddle** node or **Ritual** node depending on the player’s choice, with further branches gated by reputation or items. This graph and the current state can be tracked easily (and even stored on-chain if needed, e.g. in the player’s progress token or in the indexer state).

All the dialogue content itself is stored immutably on-chain (in the ordinal libraries) rather than hard-coded. As described above, each governor has a **compressed dialog library** containing their speech lines and narrative snippets. The game logic references these by ID or index. A given dialog state will correspond to a key in that JSON (for instance, `node_5_question` or `riddle_fail_response`). The library is structured to allow **multiple variants** of the same response for variety. For example, the governor might have three different phrasings for a greeting, labeled under an `"intro_responses"` list. The engine can pick one deterministically using some entropy from the blockchain (e.g. current block hash or a TAP token RNG) to ensure all players see the same “random” choice. Because the data is on-chain, every peer in the P2P network has access to the exact same dialog lines and can therefore reach **consensus on the game state** after each interaction (no AI randomness causing divergence).

**Dialog Flow:** The interaction loop is: *Player Input → NLU Classification → Intent Category → State Machine Transition → Governor Response*. This two-phase approach cleanly separates understanding the player’s message from deciding the game outcome. In **Phase 1 (NLU)**, we take the raw text input and map it to a higher-level intent (like “player greeted the NPC”, “answered the riddle correctly”, “asked an off-topic question”). In **Phase 2 (State Update)**, we use the identified intent plus the current dialog node to determine how the governor responds and whether the conversation moves to a new state or quest. Because the mapping from input to intent is deterministic and the state machine logic is a fixed set of rules, the same input in the same context will always yield the same outcome on every device – a crucial feature for a decentralized game.

### Input Classification Without LLM (Deterministic NLU)

We implement a **lightweight Natural Language Understanding (NLU)** module to classify player inputs, entirely rule-based or using tiny models so it can run offline. The system combines **keyword/pattern matching** with the aforementioned **embedding similarity** to cover variations in phrasing. First, we define a set of expected intents for dialogues – e.g. `GREETING`, `ASK_KNOWLEDGE`, `ANSWER_RIDDLE`, `INSULT`, `OFFER_ITEM`, `GOODBYE`, etc. For each intent, we craft a few patterns or trigger phrases. For example, `GREETING` might match tokens like “hello, hi, greetings,” while `ANSWER_RIDDLE` might look for certain keywords from the riddle’s answer. These patterns (regular expressions or token sets) are stored on-chain as part of the game data (possibly within the puzzle/quest definition) so that the classification can be performed deterministically by simply checking the input against these patterns.

If a player’s input doesn’t exactly match any pattern, we fall back to a **semantic similarity check**. Using the SimpleEmbedding approach described earlier, the classifier will compare the input tokens to the tokens in intent patterns via cosine similarity. This allows, for instance, that “good day” can be recognized as a greeting because its words have similar embeddings to “hello” (even if the exact word isn’t in the list). The engine computes a similarity score and if it exceeds a threshold, treats it as a match. All of this is done with basic linear algebra – no external API calls or large model inference – so it’s fast and reproducible on any node. In code, the `IntentClassifier` classifies text by first trying exact token matches, then checking semantic similarity for medium-confidence cases. This mirrors our approach: **exact matching for precision, fuzzy matching for recall**. The outcome is an `IntentCategory` plus maybe some extracted entities (e.g. if the input mentions an item’s name, a simple regex can capture that for the quest logic).

By keeping the NLU deterministic, we ensure *same input → same intent* across all players’ devices. This classified intent is then fed into the state machine.

### Trait-Based Response Selection and Quest Triggers

Every governor has an **archetypal profile** encoding their personality traits, motives, tone, and preferences. This profile influences how they respond within the dialog framework. We use a trait-based rules engine: essentially a set of if-then rules or selectors that modify dialog selection based on the governor’s profile. For example, a governor whose profile JSON might contain:

```json
{
  "tone": "SOLEMN_CRYPTIC",
  "puzzle_style": "METAPHOR",
  "greeting_preference": "FORMAL",
  "response_style": "RIDDLES",
  "triggers": ["RITUAL_GESTURE", "SACRED_KNOWLEDGE"]
}
```

&#x20;will behave differently from one with a jovial tone or direct style. In practice, we implement this by tagging or grouping the response lines in the dialog library and by using conditional logic when choosing a line. For instance, the **governor’s greeting**: if `greeting_preference` is `"FORMAL"`, the engine will select from a list of formal greetings (“*Greetings, seeker of truth.*”) rather than a casual “Hey there.” The dialog library can store both options, and the profile serves as a key to pick the appropriate subset. Similarly, if `response_style` is `"RIDDLES"`, then whenever the governor gives information, we pull from riddle-like responses (perhaps stored under a `knowledge_answers` category that has cryptic versions of facts). We essentially **filter or weight the selection of pre-written lines** based on traits.

Traits also influence the **game logic**: The profile’s `triggers` might list special player actions or keywords that this governor particularly responds to. For example, a governor with `"RITUAL_GESTURE"` in triggers might require the player to perform a certain emote or phrase to initiate a secret quest. The NLU will detect those trigger words or actions in input and then the state machine checks the governor’s profile for a match. If it matches a trigger, it transitions into a special branch (launching a ritual mini-quest or revealing hidden knowledge). This is how *quests are triggered* deterministically: by rule-based checks of input against trait-defined triggers. Because each governor’s triggers and quest hooks are known (in their profile or quest data), the engine can simply do an `if` check – **no AI guesswork needed**. For instance:

```python
# Pseudocode example
if "RITUAL_GESTURE" in governor_profile["triggers"] and intent == IntentCategory.PERFORM_GESTURE:
    start_ritual_quest()
```

In the codebase, similar trait references are used to adjust behavior – e.g. a “patient” trait might allow leniency in puzzles, a “meticulous” trait might require exact answers. We apply the same approach to dialog: if a governor is noted as *stern*, responses might be shorter and more curt. These conditions are coded into the dialog manager. The result is each governor feels distinct: their **virtues and flaws affect gameplay**. A benevolent governor might give extra hints on failure, whereas a prideful one might chastise the player for ignorance. We can implement this by having multiple response variants for failure cases and using the trait flags to choose one. For example, a kind governor’s `"failure_hints"` might include gentle encouragement, while a proud governor’s `"failure_hints"` are scolding or refuse to help.

Finally, because all dialog outcomes are predetermined by these rules and selections, initiating and completing quests is straightforward. If the player says the right phrase or meets the right condition (as checked by the dialog logic), the engine will transition the state machine into the quest state. The quest data (likely stored under `questlines/` for that governor) can then be loaded and similarly driven by deterministic steps (e.g. a sequence of puzzles or tasks). The **Trac protocol integration** ensures that quest progress can be recorded on-chain (perhaps via tokens or inscriptions that mark puzzle completion), but the dialog engine’s role is to present the quest narrative and check triggers.

### Maintaining Archetypal Voice and Tone

Even though responses are static, we ensure **every line is delivered in the governor’s unique voice**. This is achieved by careful writing and by templating responses with each character’s tone. Each governor’s profile defines attributes like tone (e.g. *solemn, enthusiastic*), formality, and even typical sayings. All the dialog content for that governor is written to reflect those attributes – for example, a governor with `tone: "SOLEMN_CRYPTIC"` will have verbose, cryptic lines filled with mystic language, whereas one with `tone: "CASUAL_BLUNT"` might have short, snappy lines. The dialog engine **never outputs a line that isn’t pre-approved for that character**. If an unexpected input comes (something we didn’t anticipate in any pattern), we don’t let the governor suddenly break character. Instead, we have a **default fallback response** unique to each governor’s personality. The design calls for a catch-all like “*Your words stray from the matter at hand...*” said in the governor’s style, to handle any nonsense input. This way, the immersion is never broken – there’s always a deterministic line the governor can say, and it will **sound like them**.

To implement this, we include in each governor’s dialog library some generic lines (e.g. an idle response, a confused response) that match their voice. We also leverage minor templating: for instance, many governors address the player with a certain epithet (“Seeker”, “Mortal”, “Child”, etc.). We store that in their profile and then construct some lines dynamically by inserting the epithet. Since it’s a fixed string substitution, it’s still deterministic and doesn’t require an AI. Similarly, if referencing something the player did or an item, the governor’s phrasing can be generated from a template: e.g. *"{player\_name}, you have proven yourself {adjective}."* – where `{adjective}` might be “worthy” for a kind mentor-type governor or “less ignorant than most” for a haughty one. These adjectives or small snippets can be tied to traits and stored in a lookup table. Using this approach, we ensure **consistent tone and vocabulary**. The governors effectively have a style guide baked into their data.

In summary, the Governor Dialog & Quest Engine uses **deterministic logic and curated content** to simulate an AI-like interaction. It classifies player inputs via rules (with possible small-vector semantic help), then uses the state machine and trait rules to pick an appropriate response. The design guarantees that governors always respond in an **archetypally consistent way**, because every possible response is rooted in their predefined profile and dialog scripts. This LLM-free approach avoids unpredictability while still allowing rich, context-sensitive conversations. And since everything (knowledge base, dialog lines, quest scripts) lives on-chain in the Lighthouse, the game achieves a fully decentralized narrative engine with no external dependencies, exactly as required. All that’s left is for a developer to implement these structures – many of which are already outlined in the repository (e.g. knowledge schemas, intent classifiers, and dialog templates) – and deploy them via Ordinal inscriptions. The result will be a **self-contained on-chain RPG engine** where the Lighthouse provides the wisdom and the governors provide the personality, all without a single API call to an LLM.
